# Манифест: Резервное копирование и восстановление

**ТЗ 12.5 и 16:** «Настроено резервное копирование», «Инструкция по резервному копированию и восстановлению».

## Что бэкапим и почему именно это

| Объект | Почему | Как |
|---|---|---|
| База `alyaev` | заявки, контент, цены — то, что нельзя восстановить из кода | `pg_dump -Fc` |
| Файлы загрузок | документы и изображения клиентов | `alyaev-media-YYYY-MM-DD_HHMMSS.zip` |
| `.env` | пароли и настройки | **не в бэкап** — секреты живут отдельно |

**Схема БД в бэкапе не главное** — она воспроизводится миграциями из репозитория.
Главное — данные. Именно поэтому бэкап схемы (например, `pg_dump --schema-only`)
не считается достаточным.

## Формат и имя

| Что | Имя | Формат |
|---|---|---|
| База | `alyaev-YYYY-MM-DD_HHMMSS.dump` | `pg_dump -Fc` (сжатый, `pg_restore`, выборочное восстановление) |
| Файлы | `alyaev-media-YYYY-MM-DD_HHMMSS.zip` | zip каталога `media` |

Оба файла получают одну и ту же отметку времени, поэтому база и файлы всегда парные.
Имя с датой и временем: бэкапы не перезаписывают друг друга.

**Если файлов нет**, zip не создаётся и в логе пишется «Файлов нет — архив media пропущен».
Пустой архив не появляется: он бы только создавал видимость бэкапа.

## Хранение

| Правило | Значение |
|---|---|
| Глубина | 14 дней (2 недели) |
| Минимум копий | 7 — старые не удаляются, пока не набралось 7 |
| Каталог | `E:\DockerData\alyaev-it\backups` |

**Правило:** ротация удаляет только по возрасту И только если остаётся не меньше 7 копий.
Иначе сбой расписания мог бы стереть все бэкапы разом.

Ротация учитывает **оба типа файлов** (`.dump` и `media-*.zip`) — иначе архивы файлов
копились бы вечно.

**Ловушка, на которой ротация уже молчала:** `Get-ChildItem -Include` без `-Recurse`
на каталоге возвращает **0 файлов** (проверено: без `-Recurse` — 0, через `Where-Object` — 4).
Скрипт считает файлы через `Where-Object`, а не через `-Include`.

В ротацию попадают **только файлы самого скрипта** — с именем
`alyaev-DATE_TIME.dump` / `alyaev-media-DATE_TIME.zip`. Чужие файлы в каталоге
(например `pre-migration_*.dump`) ротация не трогает: это не её имущество.

## Проверка бэкапа, а не факта его создания

Бэкап, который ни разу не восстанавливали, — это надежда, а не бэкап.

Скрипт `verify-backup.ps1` восстанавливает последний дамп в **временную** базу
`alyaev_verify`, сверяет число строк в ключевых таблицах с рабочей базой,
и удаляет временную базу. Рабочая база не трогается никогда.

## Восстановление

`restore.ps1 -File <дамп>` — восстанавливает в рабочую базу.

**Обязательное правило:** перед восстановлением скрипт делает страховочный бэкап текущего
состояния. Восстановление по ошибке без этого уничтожило бы данные, которые ещё целы.

## Чего НЕ делаем

- Не кладём бэкапы в git — там личные данные клиентов.
- Не храним `.env` внутри дампа.
- Не восстанавливаем «на всякий случай» — только по явной команде с указанием файла.

## Каталог media

Загруженные файлы лежат в `E:\DockerData\alyaev-it\media` (bind-mount в `/app/media`),
не внутри образа и не в базе. В дамп базы они **не попадают** — поэтому `backup.ps1`
упаковывает каталог отдельным zip-архивом в том же проходе.

Причина: в дампе базы только метаданные (`uploaded_files`), а сами файлы на диске.
Восстановили базу без `media` — получили записи, указывающие в пустоту.

Восстановление файлов — распаковать `alyaev-media-*.zip` в `E:\DockerData\alyaev-it\media`
**после** восстановления базы. Пары не перепутать: отметка времени у дампа и архива совпадает.


## Проверка копии (обязательно)

Копия, которую не проверяли, — не копия, а надежда. Правила:

1. **Сверяются ВСЕ таблицы**, а не список из пяти. Список берётся запросом к `pg_tables`,
   поэтому новая таблица попадает под проверку автоматически и её нельзя забыть.
2. **Отсутствующая в копии таблица — это расхождение**, а не ошибка скрипта.
   Вывод читается как `РАСХОЖДЕНИЕ solutions : рабочая=2 бэкап=нет таблицы`.
3. **Результат пишется в лог** `E:\DockerData\alyaev-it\logs\verify-backup.log`.
   Планировщик не видит stdout — без файла результат проверки пропадает молча.
4. **Код выхода 1 при расхождении.** Планировщик показывает его в «Последний результат».

Задача планировщика: **`AlyaevIT-BackupVerify`**, ежедневно в 04:30 (после ночного бэкапа).
Запуск вручную:

```powershell
powershell -ExecutionPolicy Bypass -File infra\scripts\verify-backup.ps1
# проверка конкретной копии:
powershell -ExecutionPolicy Bypass -File infra\scripts\verify-backup.ps1 -File <путь к .dump>
```

### Как понять, что копия на самом деле сломана

Проверено 24.11.2026: старые копии за 14:01–14:04 не содержали таблиц `articles`,
`portfolio`, `solutions`, `semantic_queries`, `article_services`. Это **не дефект бэкапа** —
эти таблицы появились миграцией в 14:16, позже дампа. Старая копия честно отражает состояние
на момент снятия.

Признак настоящей проблемы: свежая копия расходится с рабочей базой. Тогда смотреть лог,
а не время создания строк.
