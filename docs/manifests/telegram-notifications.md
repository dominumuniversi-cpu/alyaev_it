# Манифест: Уведомления о заявках в Telegram

**ТЗ 9.2, 14 («Уведомления о заявках в Telegram» — приоритет высокий), 16 (критерий приёмки).**

## Зачем

Заявка, о которой узнали через сутки, — это потерянный клиент. Сайт складывает заявку
в базу, но пока владелец не откроет админку, он о ней не знает. Бот закрывает этот разрыв.

## Как включается

| Переменная | Назначение | Где взять |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | токен бота | @BotFather → `/newbot` |
| `TELEGRAM_CHAT_ID` | кому слать | свой user id или id группы |

**Обе пусты → уведомления выключены, и это нормальный режим.** Сайт работает, заявки пишутся,
просто молча. Никаких падений и заглушек.

Если задан только токен, а `chat_id` нет — тоже молчим: бот не знает, куда писать.

## Правила

1. **Уведомление никогда не ломает приём заявки.** Заявка уже сохранена и подтверждена
   пользователю. Ошибка Telegram (сеть, лимит, неверный токен) пишется в лог и **глотается**.
2. **Отправка не задерживает ответ.** Пользователь не должен ждать Telegram.
   Отправляем в фоне, ответ отдаём сразу.
3. **Персональные данные — только владельцу.** В сообщении имя, контакт и текст задачи.
   Ничего лишнего: ни IP, ни user-agent, ни служебных id.
4. **Экранирование обязательно.** Имя и текст заявки приходят от постороннего человека.
   Отправляем через `parse_mode` **без HTML/Markdown** — тогда спецсимволы не ломают разметку
   и нельзя подсунуть ссылку.

## Что уходит в сообщение

```
🔔 Новая заявка с сайта
Имя: Иван
Контакт: @ivan (telegram)
Задача: автоматизация заявок
Сообщение: Нужен бот для приёма заявок...
Страница: /contacts
```

Пустые строки не показываем — «Задача: » без значения выглядит как сбой.

## Чего не делаем

- Не отвечаем клиенту от имени бота — это отдельная задача (#33).
- Не делаем кнопок «принять/отклонить» в сообщении: кнопка без серверной логики — обман.
- Не отправляем повторно при ошибке в цикле: одна попытка, дальше — лог.

## Проверка

```powershell
# бота настроили? покажет, распознаётся ли токен
docker exec alyaev-api python -c "from app.core.telegram import is_configured; print(is_configured())"
```

Сквозная проверка — отправить тестовую заявку с сайта и увидеть сообщение в Telegram.
Без токена проверить нельзя: это единственное честное доказательство.

## Как устроена доставка на этом сервере (уточнено 24.11.2026)

Первый диагноз «Docker заблокирован» оказался неполным. Проверка на живом стенде дала
такую картину:

1. **Telegram напрямую недоступен ниоткуда** — ни из контейнера, ни с хоста.
   Без прокси не соединяется даже сам хост (curl отдаёт код 000).
2. **Весь доступ идёт через локальный прокси** `127.0.0.1:10809`.
3. **Прокси принимает только с `127.0.0.1`.** По адресу хоста в docker-сети
   (`host.docker.internal` = `192.168.65.254`) соединение отклоняется.
   Поэтому контейнер через этот прокси ходить не может в принципе.

Отсюда схема: **уведомления отправляет скрипт на хосте**, а не backend.

| Что | Где |
|---|---|
| Приём заявки и сохранение | backend, контейнер |
| Отправка в Telegram | `infra/scripts/telegram-notify.ps1`, хост Windows |
| Что уже отправлено | `E:\DockerData\alyaev-it\telegram-state.json` |
| Журнал отправок | `E:\DockerData\alyaev-it\telegram-notify.log` |

Скрипт читает заявки за последние 7 дней, отправляет те, которых нет в файле
состояния, и запускается планировщиком (`AlyaevIT-TelegramNotify`) каждые 5 минут
от имени SYSTEM. Одна заявка — ровно одно сообщение.

### Почему прокси прописан в скрипте явно

Планировщик запускает скрипт от SYSTEM, а у SYSTEM переменных `HTTPS_PROXY` нет.
Без явного адреса запрос висит до таймаута, хотя через прокси Telegram отвечает
мгновенно. Поэтому адрес зашит как значение по умолчанию и переопределяется
параметром `-Proxy`.

### Проверка

```
powershell -File E:\DockerData\alyaev-it\scripts\telegram-notify.ps1 -DryRun
powershell -File E:\DockerData\alyaev-it\scripts\telegram-notify.ps1
```

`-DryRun` печатает, что было бы отправлено, и ничего не шлёт.

### Видно, сколько заявок ждёт включения

Пока токен не задан, скрипт на каждом круге (раз в 5 минут) пишет в журнал не просто
«уведомления выключены», а **сколько заявок лежит в базе за 30 дней**:

```
внимание: уведомления выключены, а в базе 2 заявок за 30 дней. Задайте TELEGRAM_BOT_TOKEN и TELEGRAM_CHAT_ID
```

Зачем: заявка, о которой не узнали, — потерянный клиент. Молчаливый режим выглядел
одинаково и когда никто не писал, и когда писали каждый день. Теперь разница видна
одной строкой в журнале, без открытия админки.

### Как выглядит успех и ошибка

Успех в журнале: `заявка N отправлена`.
Неверный токен: `заявка N не отправлена: (401) …`, и заявка **не** помечается
отправленной — повтор на следующем запуске. Проверено на живом стенде.

### Зачем тогда код в backend

`app/core/telegram.py` оставлен как второй путь: если сеть когда-нибудь пустят
напрямую, достаточно задать `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`, и backend
сам начнёт слать с задержкой ноль. Сейчас эти переменные пустые, поэтому backend
молчит и дублей не будет.
