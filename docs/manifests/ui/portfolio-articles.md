# Манифест: Портфолио и статьи

**ТЗ 5 блок 6, 11.6, 12.3:** кейсы и статьи ведутся из админки, статус кейса честно указан,
soft-delete вместо физического удаления.

## Портфолио

| Поле | Обязательное | Правило |
|---|---|---|
| `slug` | да | уникален, латиница, дефисы |
| `title` | да | ≤ 200 |
| `summary` | да | ≤ 320 — что за проблема решалась |
| `problem` / `solution` | да | текст, markdown |
| `technologies` | да | список строк |
| `status` | да | `demo` / `own` / `commercial` |
| `published` | да | черновик/опубликовано |

### Что должна содержать страница кейса (ТЗ 5 блок 6)

ТЗ перечисляет девять атрибутов. Где каждый живёт сейчас:

| Атрибут ТЗ | Где на странице | Статус |
|---|---|---|
| Название | `title`, H1 страницы | есть |
| Проблема, которую решает | `problem_md`, раздел «Проблема» | есть |
| Архитектура решения | `solution_md`, раздел «Как устроено решение» | есть |
| Используемые технологии | `technologies`, метки под H1 | есть |
| Статус (демо / свой / коммерческий) | `status`, метка первой | есть |
| Изображение | — | **нет** |
| Демонстрация работы | внутри `solution_md` подзаголовком | текст есть, отдельного блока нет |
| Результат тестирования | внутри `solution_md` подзаголовком | текст есть, отдельного блока нет |

**Решение:** демонстрация и результат тестирования остаются подзаголовками `## ` внутри
`solution_md`, а не отдельными колонками. Причина: у демонстрационных проектов результат
тестирования часто пуст или это одна фраза, и отдельное поле заставляло бы редактора
выдумывать содержимое, чтобы форма не пустовала. Подзаголовок исчезает вместе с абзацем —
пустых блоков на странице не появляется (требование ТЗ 16: «нет пустых блоков»).

**Изображение** — осознанно отложено, см. раздел «Чего нет и почему намеренно».

### Статус кейса — обязателен и честен

| Статус | Показывается как | Когда ставить |
|---|---|---|
| `demo` | «Демонстрационный проект» | свой образец, не внедрение у клиента |
| `own` | «Собственная разработка» | внутренний проект |
| `commercial` | «Коммерческое внедрение» | был реальный заказчик |

**Запрещено (ТЗ 5 блок 6):** указывать вымышленную экономию, проценты эффективности,
число клиентов. Поля для таких цифр в схеме есть только на будущее и заполняются
после реальных измерений — на публике пустые поля не показываются.

## Статьи

| Поле | Правило |
|---|---|
| `slug` | уникален |
| `title` | ≤ 200 |
| `excerpt` | ≤ 320, для списка блога |
| `body_md` | markdown, ≤ 100 000 |
| `status` | `draft` / `published` / `archived` |
| `published_at` | ставится автоматически при первой публикации |

**Правило даты:** повторное сохранение опубликованной статьи **не меняет** `published_at`.
Обновление ради «свежей даты» обесценивает блог и вводит читателя в заблуждение.

## Soft-delete

Удаление ставит `deleted_at`, запись остаётся в базе и исчезает с сайта.
Физическое удаление — только администратором и только через базу, не из интерфейса.
Причина: случайно удалённую статью можно вернуть, удалённую физически — нет.

## Публикация

Сайт показывает только `published` и `deleted_at IS NULL`. Черновик виден по прямому
адресу только после входа с правом `content:read`.

## Как это показывается на сайте

| Ситуация | Портфолио | Блог |
|---|---|---|
| В базе пусто | встроенный демонстрационный набор | честный текст, без пустого блока |
| Есть опубликованное | карточки из базы, встроенный набор скрыт | лента из базы |
| Черновик | не виден | **404** по прямому адресу |
| Удалён (soft-delete) | не виден | **404** |

**Статус на карточке пишется словами**, а не кодом: `demo` → «Демонстрационный проект»,
`own` → «Собственная разработка», `commercial` → «Коммерческое внедрение».
Посетитель не должен видеть `demo` в интерфейсе.

## Перелинковка статьи с услугами (ТЗ 11.10)

Схема и правила хранения — `db/schema.md` п. 12.3 (`article_services`).
Здесь — только правила интерфейса.

- Блок «Услуги по теме статьи» стоит **после текста статьи, до финального CTA**.
  Порядок неслучаен: сначала читатель получает пользу, потом видит, куда идти.
- Связанных услуг **не больше трёх**. Пять ссылок под статьёй читаются как реклама.
- Каждая карточка: название услуги, краткое описание, цена «от».
- **Нет связей — нет блока.** Заголовок без содержимого хуже отсутствия блока.
- Связи ведёт человек по смыслу. Автоподбор по ключевым словам даёт пары вроде
  «статья про отчёты» → «разработка сайтов» и вредит перелинковке.
- Ссылка ведёт на живую страницу услуги. Если услуга снята с публикации
  (`status != 'published'` или `deleted_at`), она в блок не попадает — это
  обеспечивает запрос, а не проверка в коде страницы.
- Обратное направление — на странице услуги блок «Готовые решения по этой теме»
  (`ui/solutions-library.md`), через `solutions.service_slug`.

## Чего нет и почему намеренно

**Изображения кейсов.** Поле `cover_image` в схеме нет, на странице картинки нет.
Причина: у демонстрационных проектов нет скриншотов, которые можно честно показать
(интерфейсов в привычном виде у ботов и интеграций мало). Рисовать «заглушку с ноутбуком»
или подставлять чужие картинки — значит выдавать несуществующее за реальное, а это прямой
запрет ТЗ 5 блок 6 и ТЗ 16 «нет пустых блоков и заглушек». Картинки появятся, когда
будут настоящие скриншоты работающих систем.

**Числовые показатели эффективности.** Полей под проценты и суммы нет намеренно:
любая цифра до реальных измерений — выдумка.

## Блок «Читайте также» (перелинковка статей, ТЗ 11.10)

Показывается на странице статьи **после текста и перед блоком услуг**.

| Свойство | Правило |
|---|---|
| Источник данных | `GET /api/v1/public/articles-related/{slug}` → таблица `article_articles` |
| Количество | Не больше 3 — ограничение в запросе, не в вёрстке |
| Порядок | Сначала новые (`published_at` по убыванию) |
| Состав | `h2` «Читайте также» + карточки-ссылки с заголовком статьи |
| Пусто | Блок не рендерится целиком — ни заголовка, ни пустой сетки |
| Черновики | Не показываются ни как источник, ни как цель |
| Ссылка | `/blog/<slug>/`; `href` есть в HTML без JS |

Правила подбора связей (ручные, не автоматические):

1. Связь направленная; взаимность заводится двумя строками осознанно.
2. Связывать только статьи, где читателю есть смысл идти дальше по теме.
3. Не ставить две статьи, конкурирующие за один запрос в одну связку,
   если одна из них — обзорная.
