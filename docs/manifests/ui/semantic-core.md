## 1. Зачем это существует

Не для красоты отчёта. Ядро отвечает на три вопроса, на которые иначе отвечают
догадками:

1. **Что мы целимся занять** — списком запросов с частотностью.
2. **Какой страницей** — обязательным `target_path`.
3. **Получилось ли** — позицией и датой её проверки.

Если запрос не привязан к странице, с ним нельзя работать: непонятно, кого улучшать.
Поэтому `target_path` обязателен на уровне БД.

## 2. Поля

| Поле | Тип | Обязательное | Что значит |
|---|---|---|---|
| `query` | текст | да, 2–200 | Сам поисковый запрос |
| `group_slug` | список | да | Группа из ТЗ 11.4 (см. §3) |
| `target_path` | путь | да, ≤255 | Целевая страница, без замыкающего слеша |
| `priority` | список | да | `high` / `medium` / `low` |
| `frequency` | целое или пусто | нет | Частотность; **пусто ≠ 0** |
| `frequency_source` | текст | нет | Откуда цифра: `wordstat` / `gkp` / `hand` |
| `difficulty` | 0–100 | нет | Конкурентность; пусто = не оценивали |
| `region` | текст | да, по умолчанию `ru` | Регион запроса |
| `position` | 1–1000 или пусто | нет | Текущая позиция; **пусто = выпал из выдачи** |
| `position_checked_at` | дата | ставит сервер | Когда проверяли позицию |
| `cluster` | текст | нет | Подтема внутри группы |
| `notes` | текст | нет | Заметки: почему выбрали этот запрос |

## 3. Группы — закрытый список

`telegram`, `ai`, `rag`, `automation`, `parsers`, `integrations`, `websites`.

Список из семи направлений повторяет ТЗ §11.4. Свободная строка группы
превратила бы ядро в свалку с опечатками («телеграм» и «telegram» — разные группы).
Расширять — правкой `GROUPS` в `app/api/admin_semantic.py` **и** таблицы в ТЗ,
а не вводом руками.

## 4. Три свойства, которые легко испортить

### Пусто — это не ноль

`frequency = NULL` значит «не измеряли». `frequency = 0` значит «измерили, спроса нет».
Это разные решения о работе: первое — надо сходить в Вордстат, второе — не трогать.
Сортировка ставит неизмеренные в конец (`nullslast`), иначе они случайно
оказываются то сверху, то снизу.

С той же логикой `position = NULL` значит «выпал из топ-1000 или не смотрели»,
а не «нулевая позиция».

### Одна страница — много запросов, но не наоборот

Нормально: пять формулировок ведут на одну страницу услуги. Так и должно быть.
Плохо: **два разных запроса одной группы ведут на две разные страницы** — они
начнут конкурировать друг с другом, и поисковик выберет не ту. Это называется
каннибализацией, и лечится объединением страниц, а не новыми запросами.

Отчёт `GET /api/v1/admin/semantic/summary` как раз показывает раскладку
«страница → сколько запросов»: одна страница со множеством запросов — здоровая картина.

### Путь нормализуется так же, как SEO

`target_path` хранится с ведущим слешем и **без** замыкающего: `/services/telegram-bots`.

**Важно, и это не опечатка:** `seo_metadata.path` хранится **с** замыкающим слешем
(`/services/`), потому что это адрес страницы для sitemap и canonical.
`semantic_queries.target_path` — **без** замыкающего, потому что это путь для
сопоставления запросов с конкретной услугой или статьёй.

Поэтому при сравнении ядра с SEO-панелью путь нормализуется — убрать замыкающий
слеш. Без нормализации одна и та же страница выглядит как две разные, и сверка
«у каждой ли страницы есть ядро» врёт.

## 5. Адреса API

| Действие | Метод и путь |
|---|---|
| Список с фильтрами | `GET /api/v1/admin/semantic?group=&target=&priority=` |
| Сводка по страницам | `GET /api/v1/admin/semantic/summary` |
| Добавить запрос | `POST /api/v1/admin/semantic` |
| Изменить запрос | `PATCH /api/v1/admin/semantic/{id}` |
| Записать позицию | `POST /api/v1/admin/semantic/{id}/position` |
| Удалить запрос | `DELETE /api/v1/admin/semantic/{id}` |

Позиция вынесена в отдельный вызов намеренно: её меняют часто и по одному,
а остальные поля — редко. Общий `PATCH` с позицией заставлял бы присылать
все поля ради одного числа.

## 6. Правила работы (ТЗ §11.8)

1. Ядро **наполняется вручную** через админку. Парсера выдачи нет и не будет:
   Яндекс и Google блокируют автоматические запросы, а «серые» способы нарушают их правила.
2. Частотность — из Яндекс Вордстат (регион «Россия»), вписывается с пометкой источника.
3. Позиции проверяются **раз в квартал**. Дата проверки ставится сама при записи позиции.
4. Ядро пересматривается раз в квартал: запросы без переходов за квартал — кандидаты
   на удаление, а не на «пусть полежит».

## 7. Чего здесь нет и почему

- **Автоматической проверки позиций** — см. §6.1.
- **Связи с `seo_metadata.keywords`** — не дублируем. `keywords` это снимок для
  поисковика (и, к слову, Google его не использует), ядро — рабочая таблица.
  Переносить данные между ними не нужно.
- **Мягкого удаления** — у ядра нет истории, которую жаль потерять. Запрос либо
  актуален, либо удаляется. Если нужен архив — это отдельная задача, а не «на всякий случай».
