# Правила разработки — alyaev.it

Обязательны для любой новой страницы, блока, кнопки, API или таблицы.

## 0. Закрытие задач: по каждому пункту, а не по ощущению

Задача из задачнике — это контракт. Её тело перечисляет требования; закрытие означает,
что **каждое** из них проверено вживую.

**Запрещено** закрывать задачу, если часть пунктов не сделана. Нельзя закрыть «в основном»,
«остальное потом», «это и так понятно». Если пункт неприменим (например, WebP, когда на сайте
нет изображений) — это пишется в задаче явно как «неприменимо» с причиной.

**Порядок закрытия:**

1. Выписать пункты требования буквально из тела задачи.
2. Поставить напротив каждого: сделано / неприменимо (почему) / не сделано.
3. Если есть «не сделано» — задача остаётся открытой, а в задачу дописывается реальный статус.
4. Проверять вживую (curl, страница, БД), а не по факту существования файла.

**Проверено жизнью:** задача #45 была закрыта с одним пунктом из четырёх. Осталась незаметной
потому, что закрытие выглядело завершённым. Такое закрытие хуже открытого долга: оно прячет работу.

## 1. Перед началом

1. Открыть **GitHub Issues** репозитория — найти задачу, если нет — завести issue с ID вида `T1-08`. `TASKS.md` — только оглавление, статусов в нём нет.
2. Прочитать `docs/manifests/ui/tokens.md` (цвета/шрифты/отступы).
3. Если работа с данными — прочитать `docs/manifests/db/schema.md`.
4. Если новый элемент интерфейса — проверить, нет ли готового манифеста в `docs/manifests/ui/`.

## 1a. Три источника правды — не путать

| Знание | Где живёт |
|---|---|
| Задачи и их статусы | **GitHub Issues** репозитория |
| Решения, ловушки, найденный опыт | **kaeru**, инициатива `alyaev` |
| Правила, манифесты, схема БД, ТЗ | **Markdown-файлы** в репозитории |

Дублировать статусы задач в файлах запрещено — расходится. 
Найденное решение или неочевидную ловушку записывать в kaeru, а не только в коммит.

## 1b. ТЗ как источник, а не догадка

У проекта два документа ТЗ:

| Документ | Где | Статус |
|---|---|---|
| ТЗ v1.0 (24.11.2026) | `docs/spec/TZ_v1.docx`, текст в `docs/spec/TZ_v1.md` | **главный**, при расхождении побеждает он |
| Исходное ТЗ | в тексте задачи-цели | историческое, тот же смысл в разделе про сайт |
| Конспект первого сообщения | раздел 1-18 | детализирующий, не противоречащий |

**Правило:** перед разработкой блока сверить его с ТЗ v1.0. Если код расходится с ТЗ — это дефект кода,
пока не доказано обратное. Не додумывать требования, которых нет в ТЗ.

### Приоритеты P0-P3

| Приоритет | Что | Правило |
|---|---|---|
| P0 | Публичный сайт, лидогенерация, SEO, базовая админка | нужно для первого релиза |
| P1 | Кабинет клиента, проекты, документы, обращения | следующий этап |
| P2 | Telegram: бот, привязка, канал | после кабинета |
| P3 | Оплата, подписки, платные материалы | вне текущего объёма |

Не начинать P2, пока не закрыт P0. Не обещать P3 как часть работы.

## 1c. Публичное и служебное разделено

- Публичный контент — SSR, есть в HTML без JS, индексируется.
- Кабинет, вход, регистрация, админка, API — `noindex`, проверка прав на сервере.
- Пустой раздел (портфолио, отзывы) не публикуется и не индексируется, пока в нём нет подтверждённого содержимого.
- Версия API — `/api/v1`. Публичные, авторизованные и административные endpoints разделены по префиксам.

## 1d. Требование «клиент A не видит данные клиента B»

Проверка принадлежности объекта выполняется **на сервере при каждом запросе**, по владельцу записи,
а не по тому, что клиент прислал в ID. Обязательный тест на подмену ID — часть приёмки любой
функции кабинета. Скрытая кнопка в интерфейсе защитой не считается.

## 1e. Тексты для клиентов

Все публичные тексты — по правилам `docs/rules/COPYWRITING.md`: начинать с ситуации читателя,
термины переводить в понятное, конкретное вместо абстрактного, без выдуманных цифр и псевдо-дефицита.
Проверять по чек-листу в конце документа перед публикацией.

## 2. Манифесты

- Новый UI-компонент → манифест **сначала**, код потом. Имя: `docs/manifests/ui/<component>.md`.
- Манифест содержит: назначение, анатомию, варианты, состояния, props, примеры, антипаттерны.
- Изменение поведения компонента без обновления манифеста — дефект.
- Схема БД меняется только через `schema.md` → модель → миграция Alembic (одна миграция на задачу).

## 3. UI

- Только токены. Сырые HEX в компонентах запрещены.
- Одна primary-кнопка на видимую область.
- Никаких пустых блоков-заглушек: если данных нет — блок не рендерится.
- Мобильный вид — обязателен; проверять на 375px, 768px, 1280px.
- Все интерактивные элементы доступны с клавиатуры, имеют `:focus-visible`.
- Тексты — по-русски, деловой тон, без канцелярита и без обещаний «в 10 раз быстрее» без измерений.

## 4. Данные и API

- Публичные данные отдаются только с `status='published' and deleted_at is null`.
- Валидация на сервере всегда, UI-валидация — дополнение.
- Формы: `POST` через `fetch`, JSON-ответ, точечная смена DOM. Никаких редиректов после действия.
- Любой пользовательский ввод санитизируется перед рендером (XSS).
- Персональные данные: фиксировать `consent_version` и `consent_at`.

## 5. SEO

- У каждой публичной страницы: уникальные `title` (≤ 60 зн. ориентир) и `description` (≤ 160 зн.).
- Один `<h1>` на страницу; заголовки не перескакивают уровни.
- Один canonical; URL без дублей со слэшем/без (`trailingSlash: false`).
- Страницы `/api`, `/login`, `/account`, `/admin` — `noindex`.
- JSON-LD только там, где разметка соответствует содержимому (без фиктивных рейтингов).

## 6. Код

- Backend: Python 3.12, типы в сигнатурах, docstring у каждой функции (1–2 строки).
- Frontend: TypeScript strict, компоненты — функции, props с явным типом.
- Файл больше 300 строк — повод разбить.
- Секреты — только в окружении/`DockerData`, никогда в репозитории.

## 7. Git

- Коммиты Conventional Commits: `feat(web): ...`, `fix(api): ...`, `docs(manifests): ...`.
- Ветки: `stage/<N>-<тема>`, merge в `main` после проверки стенда.

## 8. Приёмка

- Стенд открывается, страница соответствует манифестам, форм без запросов нет.
- `nginx -t` проходит, контейнеры healthy.
- Если менялось поведение — обновлены манифест и `TASKS.md`.
